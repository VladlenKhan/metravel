# 🏖 Metravel — Веб-приложение турфирмы

Современная full-stack платформа для туристического агентства: просмотр туров, бронирование, личный кабинет и админ-панель.

**Frontend**: React 18 + TypeScript + Vite + Tailwind CSS  
**Backend**: ASP.NET Core Web API + Entity Framework Core + JWT  
**База данных**: PostgreSQL / MS SQL Server

## 2️⃣ Основной функционал

### Пользователь (клиент)

* Просмотр списка туров
* Фильтрация туров:

  * по дате начала
  * по цене
  * по городу
* Просмотр деталей тура (стоимость, экскурсии, включённые услуги, питание)
* Регистрация / авторизация
* Создание бронирования
* Покупка путёвки
* Просмотр своих бронирований

### Администратор (сотрудник турфирмы)

* Управление турами: создание, редактирование, удаление, изменение цены, количество мест
* Управление клиентами: просмотр, добавление, удаление, изменение данных
* Управление продажами/бронированиями: просмотр, подтверждение, отмена
* Просмотр аналитики и отчётов:

  * Кто из клиентов выбрал заданный город
  * Есть ли путёвки с заданной датой начала
  * Какие туры являются «горящими» (начало ≤ текущая дата + 5 дней)
  * Сколько фирма теряет из-за скидок для постоянных клиентов

### Системная логика (backend)

* Обработка бронирования:

  * Проверка авторизации и валидация данных
  * Проверка существования пользователя и тура
  * Проверка доступных мест
  * Создание записи бронирования
  * Обновление количества свободных мест
  * Сохранение транзакции
  * Возврат ответа клиенту

## 3️⃣ Архитектура backend

Мы используем **модульный монолит с чистой архитектурой + выделенный сервис бронирований (в разработке)**:

### 3.1 Монолит (MeTravel)

**Проекты и слои:**

```
MeTravel/
├─ MeTravel.Api/            ← WebAPI, Presentation Layer
│   └─ Controllers/         ← Контроллеры для туров, клиентов, бронирований
│   └─ Program.cs           ← Точка входа
│
├─ MeTravel.Application/    ← Class Library, Application Layer
│   └─ Сервисы и интерфейсы: BookingService, TourService, ClientService
│
├─ MeTravel.Domain/         ← Class Library, Domain Layer
│   └─ Сущности: Client, Tour, Booking, Service
│
├─ MeTravel.Infrastructure/ ← Class Library, Infrastructure Layer
│   └─ Репозитории, EF Core, подключение к БД
```

* **Dependencies:**

  * `Api` → `Application` → `Domain`
  * `Infrastructure` зависит только от `Domain` (репозитории используют сущности)

* **Почему несколько проектов?**

  * Контроль зависимостей
  * Легче тестировать и поддерживать
  * Можно выносить отдельные сервисы (например, Notification) без глобальных изменений

---

### 3.2 Сервис бронирований (Booking Service)

* **Идея:** вынести управление бронированиями в отдельный сервис, так как это ядро предметной области с собственной логикой, статусами и нагрузкой.
* **Задачи сервиса:**
  * создание, подтверждение и отмена брони;
  * работа со статусами (`Created`, `Confirmed`, `Cancelled`, `Completed`);
  * расчёт цены с учётом скидок.
* **Взаимодействие (планируется):**
  * монолитный backend публикует события о бронированиях (например, через RabbitMQ);
  * сервис бронирований обрабатывает эти события и ведёт свою учётную модель.
```

## 4️⃣ Схемы работы (блок-схемы)

### 4.1 От лица пользователя

* Открытие сайта → просмотр туров → фильтр (дата, цена, город) → выбор тура → регистрация/авторизация → бронирование → покупка → подтверждение

### 4.2 От лица администратора

* Вход → панель управления → управление турами / клиентами / продажами → просмотр аналитики → выход

### 4.3 От лица программного обеспечения

* Получение запроса → авторизация → валидация → проверка пользователя и тура → создание брони → обновление мест → сохранение транзакции → публикация события → уведомление → ответ клиенту

## 5️⃣ Что уже сделано / что ещё предстоит (по методичке)

### 5.1 Backend (серверная часть)

**Сделано:**

- **Архитектура:** модульный монолит на ASP.NET Core с разделением на слои `Domain / Application / Infrastructure / Presentation`.
- **База данных:** `MeTravelDbContext` с сущностями `Client`, `Tour`, `Booking`, `Service`, `TourService` и миграциями под PostgreSQL.
- **Туры:** CRUD по турам (контроллер, сервис, репозиторий, EF Core).

**Предстоит доделать (обязательно по методичке):**

- **Пользователи и роли:**
  - Сущности `User`, `Role`, `UserRole` (минимум 3–4 роли: администратор, оператор, руководитель, клиент).
  - Регистрация и авторизация (JWT): вход, выход, обновление токена.
  - Матрица прав доступа и проверки ролей в контроллерах.
- **Журнал действий (аудит):**
  - Таблица `AuditLog` (пользователь, время, тип действия, объект, результат).
  - Запись ключевых действий в журнал (создание/изменение/удаление, вход/выход и т.п.).
- **Бизнес‑процессы (сквозные):**
  - Не менее 3 процессов:
    - Поиск и бронирование тура клиентом.
    - Обработка брони оператором (подтверждение/отмена, статусы).
    - Управление турами/услугами администратором.
  - Полная реализация этих процессов и через API, и через UI.
- **Логирование и обработка ошибок:**
  - Подключение `ILogger<>` в контроллерах/сервисах.
  - Глобальный middleware/фильтр ошибок:
    - логирование исключений;
    - возврат аккуратных JSON‑ответов без утечки внутренних деталей.
- **Тестирование backend:**
  - Минимум 10 модульных/интеграционных тестов:
    - CRUD операций;
    - прав доступа и ролей;
    - бизнес‑правил и обработки ошибок.

### 5.2 Frontend (пользовательский интерфейс)

**Сделано:**

- Каркас фронтенда на **React + TypeScript + Vite + Tailwind** (дальнейшая реализация экранов в процессе).

**Предстоит доделать (по методичке и ISO 9241):**

- Ключевые экраны:
  - Вход и регистрация.
  - Главный экран (список туров + фильтры).
  - Формы создания/редактирования (туры, клиенты, бронирования).
  - Карточка тура / брони.
  - Экран результата работы модуля ИИ.
  - Экран администратора (роли, журнал действий).
- UI/UX:
  - Валидация форм (обязательность, формат, типы).
  - Понятные сообщения об ошибках и успешных действиях.
  - Базовая адаптивность под разные разрешения.

### 5.3 Модуль искусственного интеллекта (AI)

**Планируемая “фишка”:**

- **Рекомендации туров** для клиента с учётом:
  - бюджета;
  - дат поездки;
  - предпочитаемых стран/городов;
  - истории прошлых бронирований.

**Нужно реализовать:**

- Определить тип задачи (рекомендации/классификация) и признаки из БД.
- Подготовить обучающую выборку (из реальных или синтетических данных).
- Обучить модель (ML/DL), посчитать метрики качества.
- Сохранить модель в файл и загружать её при старте приложения.
- Реализовать API‑эндпоинт рекомендаций туров и интеграцию модели в backend.
- Показать результат на UI (список рекомендованных туров с пояснением).

### 5.4 Данные, БД и резервное копирование

- ER‑диаграмма в нотации «воронья лапка» с 5–10 сущностями:
  - пользователи, роли, туры, клиенты, бронирования, статусы, журнал, данные для ИИ.
- Ограничения:
  - первичные и внешние ключи;
  - уникальные индексы;
  - `NOT NULL`, справочники статусов.
- Резервное копирование и восстановление:
  - использование `pg_dump/pg_restore` (или аналогов);
  - текстовая инструкция для администратора по аварийному восстановлению.

### 5.5 Контейнеризация и развертывание

- `Dockerfile` для backend.
- Отдельный контейнер для БД.
- `docker-compose.yml` для совместного запуска:
  - сеть, тома, переменные окружения, прогон миграций.
- `.env.example` с примерами настроек.
- Инструкция запуска:
  - команды развёртывания;
  - проверка работоспособности (health‑check, тестовый запрос к API/UI).

### 5.6 Тестирование и документация

- **Тестирование:**
  - ≥10 тестов серверной части;
  - ≥10 проверок UI;
  - ≥5 сквозных сценариев бизнес‑процессов.
- **Документация:**
  - описание архитектуры (UML‑диаграммы, ER‑диаграмма);
  - руководство пользователя;
  - руководство администратора (роли, журнал, бэкапы);
  - описание API (эндпоинты, примеры запросов/ответов);
  - инструкция запуска через Docker‑компоуз.
